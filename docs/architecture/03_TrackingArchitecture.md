# 1. Purpose

This document defines the complete architecture of the Tracking Platform.

Tracking is treated as an independent platform responsible for receiving, validating, processing, storing and distributing real-time telemetry generated by bicycles during active rides.

Tracking is **NOT** responsible for business decisions.

Tracking only reports facts.

Business decisions always belong to backend business services.

---

# 2. Vision

Tracking is designed around one principle:

> **Telemetry never owns business state.**

The mobile application only reports facts.

Examples:

• GPS Position

• Speed

• Heading

• Battery Level

• GPS Accuracy

• Device Timestamp

• Connectivity

The backend decides:

• Ride Active

• Ride Finished

• Online

• Offline

• Lost Connection

• Route Deviations

• Alerts

• Storage

# 5. System Components

---

## 5.1 Mobile Tracking Engine

Runs inside the React Native application.

Responsibilities

Acquire GPS.

Monitor movement.

Detect connectivity.

Queue offline events.

Transmit telemetry.

Never changes reservation state.

Never modifies bikes.

Never performs settlement.

---

## 5.2 GPS Provider

Obtains device location.

Supported sources

Android Fused Location

iOS CoreLocation

Future

Dedicated GPS hardware

IoT modules

BLE devices

---

## 5.3 Offline Queue

Purpose

Guarantee that no GPS samples are lost.

Technology

SQLite

Responsibilities

Store pending telemetry.

Retry transmissions.

Recover after crashes.

Recover after reboot.

Support airplane mode.

The queue is FIFO.

---

## 5.4 Transmission Engine

Responsible for communication.

Priority

Socket.IO

Fallback

REST API

Responsibilities

Reconnect automatically.

Retry failed packets.

Compress payloads.

Maintain delivery order.

---

## 5.5 Tracking Gateway

Current implementation

NestJS Gateway

Future

Dedicated Tracking Service

Responsibilities

Receive telemetry.

Validate payload.

Authenticate ride.

Normalize coordinates.

Publish telemetry.

Never performs business logic.

---

## 5.6 Presence Server

Technology

Redis

Purpose

Maintain live bicycle presence.

Stores only volatile information.

Examples

Current location

Connection status

Heartbeat

Last update

Current speed

Device battery

No historical information is stored here.

Stores

Accuracy

Heading

Timestamp

Historical routes.

Heat maps.

Analytics.

Replay.

## 5.8 Business Database

Technology

Current

Routes

Business entities.

# 19. Long-Term Vision

The Tracking Platform is intentionally designed as an independent subsystem.

Its architecture allows Rent_App to evolve toward:

• Multi-city fleets

• International deployments

• IoT bicycle devices

• Embedded GPS hardware

• Smart locks

• BLE sensors

• Battery telemetry

• Predictive maintenance

• Route analytics

• AI fleet optimization

without modifying the business domains defined in the previous architecture documents.

Tracking becomes a reusable enterprise platform capable of serving any future mobility solution developed by Rent_App.
